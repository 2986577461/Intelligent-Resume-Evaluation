### 实现取舍

- 总体判断随模型JSON字符串的增量解码展示，不再等整段闭合。转义、代理对、空白跨chunk有回归测试；整体Schema在字段闭合时才完成检查，不声称增量文字已验证语义。
- 高优先级建议完整且字段/引用检查通过后立即展示。中低优先级仍等待建议数组闭合，以维持排序；追问完整且关联合法后展示。这是有真实生成进度的分层发布，不是整份生成后模拟切块，也不是所有字段逐token展示。
- 前端500ms状态播放队列已移除，正文没有人为打字节奏。
- SSE正文用 `[TEXT]` + JSON字符串无损传输，避免真实换行和字面量 `\\n`混淆，防止正文冒充 `[DONE]`/`[STATE]` 控制信号。
- 新后端需配套新前端，已有页面应刷新；没有数据库迁移，旧历史Markdown仍正常展示。

### 首轮发现并针对性修订

1. **S2技术用途预设**：原文只说用了Redis，追问却为“Redis在登录流程中具体承担什么作用”。并不能从技术名推断使用位置。
2. **S5重复质疑明确职责**：原文已写“我负责退款接口参数校验；库存架构由同组同学设计”，输出仍说“个人贡献边界不清”。
3. **S8追问虚构模块前提**：没有技能栏，追问却说“你简历上的后端技能中……”。
4. 普通解释建议时偏向QPS、规模与具体数字示例，容易给用户制造未经测量也要量化的暗示。

修订要求：原文明确职责即承认；先确认技术用途；假设性设计用条件问题；不要为所有可追问细节制造修改任务；后续聊天也遵守证据边界。没有改变验收标准，也没有放宽引用检查。
